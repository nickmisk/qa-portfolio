# 3. Замечания по требованиям

## 3.1. Недостаточно ясное требование: основные функции в онбординге

### Где

Раздел **3.1 — Онбординг пользователя**.

В требованиях указано, что при первом запуске приложения необходимо познакомить пользователя с приложением и рассказать о его основных функциях.

### Почему может быть проблемой

Не указано, что именно считается основными функциями приложения.

Из-за этого тестировщик не сможет однозначно определить, какие функции должны демонстрироваться в онбординге и какие проверки необходимо выполнить.

### Ожидаемое решение

Необходимо явно указать, какие функции приложения должны демонстрироваться пользователю при онбординге.

Например:

- просмотр подборок фильмов;
- поиск фильмов;
- фильтрация результатов поиска;
- просмотр карточки фильма;
- добавление фильма в коллекцию;
- работа с профилем пользователя.

---

## 3.2. Не указано, какие подборки являются псевдослучайными, а какие фиксированными или отсортированными

### Где

Раздел **3.2 — Вкладка «Главная»**, первый параграф.

В требованиях указано, что каждый из списков должен отображать разные псевдослучайные фильмы при каждом открытии приложения, если не сказано иного.

### Почему может быть проблемой

Формулировка **«если не сказано иного»** является неточной и допускает субъективную трактовку.

Неясно, какие подборки должны быть псевдослучайными, какие фиксированными, а какие отсортированными по определенной логике.

Из-за этого тестировщик не сможет однозначно определить ожидаемый результат при повторном открытии приложения.

### Ожидаемое решение

Для каждой подборки должно быть явно указано, какой тип отображения ожидается:

- псевдослучайная подборка;
- фиксированная подборка;
- подборка с сортировкой;
- подборка по рейтингу;
- подборка по дате выхода;
- подборка по популярности.

## 3.3. Неопределенные правила формирования истории «Вам было интересно»

### Где

Раздел **3.5 — Вкладка «Профиль»**.

В требованиях указано, что **«Вам было интересно»** отображает список фильмов, сериалов и людей, которыми пользователь интересовался.

Также указано, что размер истории нужно определить самостоятельно.

### Почему может быть проблемой

Не указано, что именно означает **«интересовались»**.

Неясно, какое действие пользователя добавляет объект в историю:

- открытие карточки фильма;
- ввод запроса в поиск;
- открытие карточки фильма определенное количество раз;
- просмотр карточки актера;
- добавление фильма в коллекцию;
- просмотр фильма в подборке.

Также формулировка **«размер истории определите самостоятельно»** не является проверяемым требованием.

Тестировщик не сможет однозначно проверить, правильно ли работает история.

### Ожидаемое решение

Должны быть описаны точные правила формирования истории:

- какие действия добавляют объект в историю;
- какие типы объектов могут попадать в историю;
- в каком порядке отображаются элементы;
- какой максимальный размер истории;
- что происходит при превышении лимита;
- удаляются ли дубликаты;
- обновляется ли позиция объекта при повторном просмотре.

## 3.4. Противоречие между автоматическим поиском и кнопкой «Применить»

### Где

Раздел **3.4 — Вкладка «Поиск»**.

В требованиях указано, что поиск должен происходить автоматически, без дополнительных кнопок, по введенному тексту и с учетом настроек.

При этом в списке настроек есть кнопка **«Применить»**.

### Почему может быть проблемой

Требования описывают два разных сценария работы поиска:

1. Поиск выполняется автоматически без дополнительных кнопок.
2. Настройки поиска применяются после нажатия кнопки **«Применить»**.

Из-за этого неясно, когда именно должны применяться настройки поиска:

- сразу после изменения настройки;
- после ввода текста;
- только после нажатия кнопки **«Применить»**;
- после закрытия экрана настроек.

### Ожидаемое решение

Необходимо явно указать, когда применяются настройки поиска:

- автоматически при изменении фильтров;
- только после нажатия кнопки **«Применить»**.

Также нужно уточнить, влияет ли кнопка **«Применить»** только на фильтры или на сам поиск тоже.

## 3.5. Неопределенное требование к фильтру «год(ы) выхода»

### Где

Раздел **3.4 — Вкладка «Поиск»**, настройки поиска.

В настройках указано поле **«год(ы) выхода»**.

### Почему может быть проблемой

Неясно, какой формат должен поддерживать фильтр:

- один конкретный год;
- диапазон лет;
- несколько отдельных лет;
- минимальный год;
- максимальный год.

Из-за этого невозможно однозначно протестировать фильтр.

Также не описано поведение при пустом или некорректном вводе.

### Ожидаемое решение

Должен быть описан формат фильтра **«год(ы) выхода»**.

Необходимо уточнить:

- допустимый формат ввода;
- минимальное и максимальное значение;
- можно ли выбрать диапазон лет;
- можно ли выбрать только один год;
- что происходит при пустом вводе;
- что происходит при некорректном вводе;
- какое сообщение об ошибке отображается пользователю.

## 3.6. Неясная формулировка: «Информация о фильмах не должна быть избыточной»

### Где

Раздел **4 — Требования к локальному хранению информации**.

В требованиях указано:

> «При добавлении фильмов в коллекции информация о них должна сохраняться в локальное хранилище, чтобы можно было отобразить пользовательские списки без дополнительных запросов к API. Информация о фильмах не должна быть избыточной.»

### Почему может быть проблемой

Спецификация не определяет, какие именно поля фильма нужно сохранять локально.

Также не указано, что считается избыточной информацией.

Из-за этого разработчики и тестировщики могут по-разному понимать, какие данные должны сохраняться в локальном хранилище.

### Ожидаемое решение

Должен быть указан минимальный набор полей для локального хранения фильма.

Например:

- `id`;
- название;
- постер;
- жанр;
- рейтинг;
- год выпуска;
- тип контента.

Также нужно указать, какие данные не должны сохраняться локально.

## 3.7. Не описано, что показывать пользователю при ошибках API

### Где

Раздел **6 — Требования UX**.

В требованиях указано, что ошибки от API должны корректно обрабатываться и не предоставлять пользователю техническую информацию.

### Почему может быть проблемой

Спецификация запрещает показывать пользователю техническую информацию, но не описывает, какие сообщения нужно показывать вместо нее.

Не указано поведение приложения для разных типов ошибок API.

Из-за этого невозможно однозначно проверить корректность обработки ошибок.

### Ожидаемое решение

Должны быть описаны пользовательские сообщения и действия приложения для основных сценариев ошибок.

Например:

- отсутствие интернета;
- ресурс не найден, ошибка 404;
- ошибка сервера, ошибка 500;
- таймаут запроса;
- пустой ответ от API;
- ошибка загрузки изображения;
- ошибка загрузки списка фильмов.

Для каждого сценария нужно указать:

- текст сообщения для пользователя;
- отображается ли кнопка повтора;
- остается ли пользователь на текущем экране;
- показывается ли заглушка;
- сохраняются ли ранее загруженные данные.

# 4. Итог анализа

В требованиях Skillcinema обнаружены следующие основные проблемы:

- неоднозначные формулировки;
- неполные правила работы функций;
- отсутствие точных критериев для проверки;
- противоречие между автоматическим поиском и кнопкой применения настроек;
- неописанные правила формирования пользовательской истории;
- недостаточно конкретные требования к локальному хранению данных;
- отсутствие пользовательских сообщений для ошибок API.

Эти проблемы могут затруднить написание тест-кейсов, выполнение проверок и определение корректного ожидаемого результата.

Перед тестированием требования желательно уточнить и дополнить.
